## 0. V8 Integration Notes (Read Before Execution)

### 0.1 How V8 Consumes This Checklist

This checklist is the contract between QA-Generator and the V8 E2E Runbook. V8 reads `{{CHECKLIST_FILE}}` (pointed to by `doc/page-list/LATEST.md`) and executes items top-to-bottom in two passes:

- **Pass 1 — SMOKE:** Every `[SMOKE]` item is executed breadth-first. No fixing. Pure breadth signal — does each route load? Does the global shell render? Do top nav and footer work? Output is a heatmap of broken vs. healthy surfaces.
- **Pass 2 — DEEP:** Every `[DEEP]` item is executed in order, with full interaction, negative paths, DB validation (where applicable via Payload Local API or psql), accessibility audits, and 5-viewport responsive sweeps. Fixing is allowed inside tier limits.

V8 owns:
- Browser automation (Playwright / Puppeteer / MCP-Playwright)
- Evidence capture (UI screenshots, console logs, network logs, DB queries)
- Tiered defect handling (Tier 1 fix, Tier 2 log, Tier 3 flag)
- Pattern Failure Escalation when ≥3 items in the same `[PATTERN-GROUP]` fail
- Blocker Bypass Protocol when a blocker prevents item completion
- Regression re-runs after fixes

The checklist owns ONLY:
- What to check (the WHAT)
- Where to capture evidence (V8 substitutes `{{REPORT_DIR}}`)
- Expected outcomes per item
- Tier hints, pattern groupings, requires-tags

### 0.2 Strict Execution Rules

1. **Browser-Only Mandate:** Every CL-XXX requires at minimum ONE browser screenshot. API-only or code-read verifications are INCOMPLETE.
2. **Atomicity:** One action, one outcome per item.
3. **Sequential IDs:** CL-001 through CL-NNN, no gaps.
4. **Evidence Paths:** Always use `${REPORT_DIR}/...` prefix.
5. **Two-Pass Tags:** Every item carries exactly one of `[SMOKE]` or `[DEEP]`.
6. **Pattern Groups:** Adjacent items testing the same subsystem share a `[PATTERN-GROUP: <name>]`.
7. **No Skipping:** Use `⏭️ BLOCKED` (cross-ref BBP-ID) — never `SKIPPED`.
8. **No multi-tenancy section.** IS does not use tenant schemas.

### 0.3 Valid Item Statuses

| Status | Meaning |
|---|---|
| ✅ PASSED | Verified with browser evidence |
| ❌ FAILED — Tier 1 | Blocking, fix attempted |
| ❌ FAILED — Tier 2 | Non-blocking, logged |
| ❌ FAILED — Tier 3 | Risky, flagged for human |
| ⚠️ PARTIAL | External service unavailable (e.g., SMTP) |
| ⏭️ BLOCKED | Depends on unfixed blocker (cross-ref BBP-ID) |

### 0.4 Completion Criteria

- 100% of `[SMOKE]` items resolved (PASSED / FAILED / BLOCKED).
- 100% of `[DEEP]` items resolved.
- Every BBP-ID in the Blocker Registry has a downstream-impact note.
- Every Pattern Registry entry has a root-cause statement.
- The Final Clean Run (Section 6) has been replayed and screenshots collected.

### 0.5 Blocker Bypass Protocol (BBP)

When a blocker prevents a checklist item from completing:

1. **BBP-1 — Detect:** V8 detects the blocker (e.g., dev server crash, DB unreachable, page hard-error).
2. **BBP-2 — Document:** V8 writes BBP-<n> to the Blocker Registry (Section 7.2) with: trigger CL-ID, blocker description, evidence path.
3. **BBP-3 — Mitigate:** V8 attempts one safe restart / dependency re-check (no code change unless tier permits).
4. **BBP-4 — Cascade-Mark:** Every downstream item that depends on the blocked surface is marked `⏭️ BLOCKED` with the BBP-<n> cross-reference.
5. **BBP-5 — Resume:** V8 continues with items that do not depend on the blocked surface.

### 0.6 Pattern Failure Escalation (Rule 12)

If ≥3 items in the same `[PATTERN-GROUP]` fail with similar root-cause symptoms:

1. **PFE-1 — Detect:** V8 detects pattern failure.
2. **PFE-2 — Register:** Add row to Pattern Registry (Section 7.3) with: pattern group, item IDs, symptom hash, hypothesized root cause.
3. **PFE-3 — Escalate:** Pause linear execution, do systemic investigation (config, middleware, shared util, env var).
4. **PFE-4 — Fix Once:** Apply one fix at the pattern level. Re-run the entire pattern group.
5. **PFE-5 — Resume:** Continue normal execution.
